# Telegram на Node.js

Модули запускаются внутри существующего `server.js`, рядом со `startTelegramWorker`.
Отдельный процесс с вторым webhook не нужен. Папка установки:
`/home/c503085/master-omkara.ru/omkara/Telegramm_bot`.

Веб-приложение и бот используют один `db.js`. Миграция 001 уже содержит
`telegram_updates`, `telegram_links`, `people.telegram_id`; миграция 002 добавляет
публикации, фото и независимые доставки по каналам. Обе миграции идемпотентны.

## Установка

1. Сохранить резервную копию изменяемых файлов и PostgreSQL штатными средствами хостинга.
2. Сверить текущие файлы сервера с исходной веткой main: пакет подготовлен на основе
   архива GitHub, полученного 20 сентября 2026. Не перезаписывать изменения сервера без сравнения.
3. Скопировать файлы пакета `omkara/` в одноимённую папку проекта. `.env` не входит в пакет.
4. Выполнить `npm ci --omit=dev`, затем `npm run migrate` из папки `omkara`.
5. Проверить переменные окружения, перезапустить приложение штатным способом NetAngels.
6. Выполнить `node --env-file-if-exists=.env scripts/telegram-webhook.js`.
   Скрипт переключает webhook, не сбрасывая ожидающие обновления; выводит только URL и счётчики.
7. Проверить `/healthz`, вход администратора, `#admin/scheduler`, загрузку и предпросмотр фото.
   Для живой проверки использовать отдельный тестовый чат, затем включить рабочие каналы.
8. Отключить Apps Script trigger `scheduler` после переключения. Иначе старый планировщик
   продолжит рассылки независимо от Node.js. Старые файлы Apps Script оставлены в репозитории для справки.

Переменные: `APP_ORIGIN=https://master-omkara.ru`, `APP_PORT`, `APP_IP`,
`DB_CONNECTION_STRING`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`,
`TELEGRAM_BOT_USERNAME`, `OWNER_EMAIL`, `NODE_ENV=production`.
Если одновременно задан `DATABASE_URL`, существующий db.js отдаёт ему приоритет;
убедитесь, что обе переменные указывают на одну БД, либо оставьте только одну.
Новый параметр `TELEGRAM_DESTINATIONS` — JSON-массив разрешённых получателей:

```dotenv
TELEGRAM_DESTINATIONS='[{"id":"-1003457344524","label":"TG:Йога"},{"id":"-1003603232471","label":"TG:Канал"},{"id":"-1003879248901","label":"TG:Онлайн ретрит"},{"id":"429751280","label":"TG:Админ"}]'
```

Эти ID перенесены из legacy Planner.txt; проверьте их актуальность и права бота.
Нет значения по умолчанию: рабочие каналы не включаются случайно.

## Поведение

- Новая строка по умолчанию выключена. Фото загружается после сохранения строки;
  на время загрузки интерфейс отключает её, затем восстанавливает выбранное состояние.
- Даты интерфейса явно в UTC. Ежедневный/еженедельный повтор — интервалы 24 часа/7 суток,
  без переходов на летнее время. Пропущенные интервалы не создают массовую рассылку.
- «Срок публикации» — абсолютный момент удаления отправленных сообщений и окончания
  повторов. Удаление зависит от прав бота и ограничений Telegram (обычно 48 часов).
  Ошибка удаления видна в статусах; после исправления прав повтор выполняется раз в час.
- Фото хранятся как bytea, доступны только admin, отправляются multipart-файлом.
  Google Drive и Telegram file_id не используются. Одноразовые фото удаляются после
  доставки всем каналам; повторяющиеся — после окончания расписания/срока.
- Подтверждённая доставка в один канал не повторяется при ошибке другого.
  После сетевого тайм-аута/падения воркера статус `uncertain` требует проверки канала:
  администратор указывает message_id уже доставленного сообщения либо явно повторяет.
  Это предотвращает автоматические дубликаты в условиях отсутствия idempotency key в Telegram.
- Есть до восьми автоматических попыток при явном временном отказе API, учитывается retry_after.
- Раздел показывает последние 200 публикаций и 500 доставок; это не интерфейс архивного поиска.

## Объём миграции старого бота

Планировщик и отправка фото адаптированы для Node.js. PropertiesService заменён env,
HtmlService — Express webhook, AppCache дедупликации — PostgreSQL telegram_updates.
Чатовые меню теперь открывают существующие защищённые разделы веб-приложения;
`/requests` читает общую БД. Пошаговые диалоги регистрации/чеков Apps Script,
VK и ежемесячный повтор не переносились: веб-регистрация и чеки остаются существующими.
Это не полная функциональная копия всех legacy-диалогов.

Google Sheets автоматически не импортируется. Для импорта нужен экспорт и явное
сопоставление людей, мероприятий, статусов и оплат; Telegram ID нельзя безопасно
использовать для автоматического создания подтверждённых email-аккаунтов.
Текущая база сайта не перезаписывается, старые записи Sheets пока остаются отдельно.

## Проверки и откат

`npm test` — PGlite + HTTP API + подменённый Telegram API. При запрете дочерних
процессов: `node --test --test-isolation=none test/scheduler.test.js`.
Тесты не отправляют сообщения в реальные каналы.
Все новые admin-маршруты используют существующие admin/CSRF/Origin проверки,
SQL параметризован, UI экранирует текст и использует textContent, URL только HTTP(S),
файлы ограничены 8 МБ, MIME сверяется с сигнатурой. Полного декодирования изображений
нет: повреждённый JPEG/PNG может быть отклонён Telegram и останется в статусе ошибки.
Секреты остаются на сервере и не выводятся в ошибки транспортного модуля.

Для отката остановить приложение, восстановить резервные копии файлов и прежний
webhook, затем запустить прежнюю версию. Добавленные таблицы можно оставить:
старая версия их не читает. Удалять данные для отката не требуется.

Документация протокола: https://core.telegram.org/bots/api
